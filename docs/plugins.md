# Native Stoke plugins

Plugin API v1 adds Settings → Plugins. Work and Grok Bot are native integrations; other packages can add text panels with Node.js actions or supported appearance overrides. Packages install disabled. Enabling is explicit, scripts run only on an action, and disabling removes the panel and stops its owned operations. This is separate from an agent's skills, MCP servers and CLI plugins.

The public directory is https://stoke.vinn.dev/marketplace, with a developer guide at /marketplace/sdk. “Open in Stoke” opens a native package review through a strictly validated stoke: link; it never installs or enables code automatically. Catalog packages are compiled from src/shared/pluginPackages.ts. Local creation writes an editable .stoke-plugin.json example to a selected folder. Import applies an edited package; Export produces a shareable copy. Public entries are curated through source review. There is no public upload endpoint.

Local command plugins run with the user's permissions. The declarations `local-code`, `project-context`, and `appearance` describe intent, not an OS sandbox. Scripts receive API version, plugin ID, data directory and optional chosen project through stdin. Stoke strips agent credentials and Node startup injection from the child environment. Output is bounded, commands have a 60-second deadline, and scripts must keep their children in the foreground. Native panels escape text; extensions cannot inject executable HTML or arbitrary CSS. Appearance overrides disappear when disabled. Removing a package preserves its saved data.

## Choose Notion tables

In Stoke **1.0.0-beta.10**, enable Work in Settings → Plugins, open its Notion connection, and enter the integration token. **Load tables** lists the data sources shared with that connection. Search by name and use **Load more tables** for additional pages. Choose a **Task table** and **Daily work table**, inspect their properties, review the suggested mappings, and save the connection. Missing databases must be shared with the connection in Notion. Discovery and inspection read metadata; they neither publish rows nor store the draft token. Saving keeps the token encrypted through the existing system key store.

The Work panel uses the direct Notion API for this picker and its reviewed publishing flow. It does not reuse an agent's MCP OAuth session. Agent Notion MCP connections remain available independently. This follows Notion's [search API](https://developers.notion.com/reference/post-search), which lists accessible data sources and supports pagination. The manual ID fields remain under a disclosure for existing configurations.

## Grok Bot accounts

Grok Bot is distinct from Grok Build's `grok` coding CLI. The native plugin uses the unofficial https://github.com/ScriptedAlchemy/grok-bot-cli, pinned to npm version 0.12.4 and reviewed source 43499fa27f36807f6ac93b56365b3cae5200bc1e. The installer verifies the npm archive SHA-512 and both runtime modules' SHA-256, extracts only reviewed runtime files plus the MIT license, and never runs npm hooks or gbot-install.

1. Install Grok Bot in Settings → Plugins, then enable it and open Details.
2. Install the reviewed CLI from its panel.
3. Sign in to the Grok Bot desktop app and connect its Computer view, choose an account nickname in Stoke, and press Read desktop sessions. Select the saved session and Import as new account. Repeat for all five accounts. Multiple descriptor slots require an explicit choice.
4. Select a Stoke account and List bots and groups to verify it. Select a bot or group and read its thread or send a message.

Stoke **1.0.0-beta.10** also distinguishes saved native logins from exported computer connections in one normal Grok Bot app. **Read desktop sessions** reads the saved-account index as well as the gateway descriptor, so five saved logins remain visible even if only two have recent computer connections. Missing and expired connections are marked in the picker and cannot be imported yet. Switch to that already-signed-in account using Grok Bot's account menu, open **Computer** and wait for it to connect, then read sessions again and import. Signing out or creating separate profiles is unnecessary. The current marker identifies the native app's saved active account; labels are generic because discovery does not decrypt private account profiles or OAuth tokens. Give each imported account a nickname. Beta.9 lists only gateway exports and lacks this saved-login discovery.

Stoke **1.0.0-beta.10** adds **Choose desktop profile folder…** for separate Grok Bot instances launched with different data folders. Beta.9 reads only the default folder, even when five instances are open. Choose the data folder from each shortcut's `--user-data-dir` argument; it must contain Grok Bot's saved-account index or `gateway-descriptor.json`. Stoke lists that folder's logins and connections without opening credentials. Give a login with a saved connection a nickname and use **Import as new account**, then choose the next folder. **Read desktop sessions** refreshes the currently chosen folder; **Use default folder** returns to the standard location. This works on Windows, macOS and Linux. On Windows, import reads `Local State` from the same selected folder, keeping different profile encryption keys separate.

Chosen folders are registered locally under opaque IDs in `plugins/grok-bot-desktop-profiles.json`. Full folder paths and OS protection keys never reach the renderer or account sync; imported production gateway snapshots can sync normally. A failed or cancelled folder choice keeps the previous selection. Selecting a missing or invalid registered profile fails explicitly instead of importing the default account. The panel returns to the default folder when reopened; choose a custom folder again to refresh that profile's login.

An existing desktop login is imported as a separate encrypted snapshot. Stoke never modifies the desktop app's auth. The nickname and gateway host identify the saved session; the gateway descriptor does not provide a verified email. Every command carries the selected gateway URL, token and routing headers explicitly and forces gateway mode, so a change in the desktop app's current login cannot change the active Stoke account.

Stoke **1.0.0-beta.8 or later** supports desktop descriptor formats 1, 2 and 3, including the v3 format written by Grok Bot 0.70.2. Beta.7 rejects v3 with “This desktop session format is not supported by the plugin yet”; updating the bot app or changing accounts does not fix that older Stoke reader. V3 snapshots expire after seven days, matching the desktop app. If Stoke reports an expired session, open Grok Bot with the intended account, load a bot to refresh its connection, then read sessions and import again. Never edit the desktop descriptor's version or paste its encrypted contents into Stoke.

If the Computer view connects but Stoke still cannot read a session, fully quit Grok Bot (Cmd+Q on Mac), reopen it, reconnect the Computer view and retry Read desktop sessions. A connected desktop can lack the saved gateway file; reopening restored it in the reported Mac case. This is also the first restart step in [Grok Bot's computer troubleshooting guide](https://cursor.com/help/grok-bot/computer-recovery). Clearing app data, changing the descriptor version and resetting the bot's computer are unnecessary for this case.

Saved credentials are not considered verified until an operation succeeds. An authentication refusal marks the account for reconnecting. To reconnect, sign in again in the desktop app, read sessions, select the correct slot and explicitly replace the chosen Stoke account. A send without confirmation is marked unknown; Stoke does not retry it. Read the thread before resending.

Beta.9 recognizes the current gateway's explicit `accepted: true` acknowledgement as well as the older message-ID receipt. Beta.8's pinned CLI labels the boolean acknowledgement unknown even though the message was accepted. The fix shows “Message sent”, clears the composer, and preserves confirmed delivery if a later account-status update fails. This follow-up is not in the published beta.8 binaries. Unknown or malformed acknowledgements still preserve the composer and require checking the thread before another send.

Beta.9 adds Grok Bot to the launcher's Other agents menu when its plugin is enabled. Choose a saved account and a bot from the left list to open its conversation. Switch bots or accounts in that list, or use New bot conversation to open another tab. Messages render headings, lists, tables and code. Live updates read recent messages every six seconds while the chat is visible, can be switched off, and stop after a failed read. Sending remains explicit; Ctrl+Enter on Windows/Linux or Cmd+Enter on Mac submits the composer.

Drafts stay with their tabs when you switch tabs or move an idle tab into another Stoke window. A send in progress stays in its owning window. These cloud tabs do not run a local coding CLI or expose local folder, model, context or terminal-shortcut controls. They are not restored from disk on restart; saved Grok Bot accounts remain encrypted, and conversation history stays with Grok Bot. Disabling the plugin closes its conversation tabs and removes its launcher choice. The account manager's Read thread also uses the formatted message view.

The advanced form accepts a session gateway tuple and routing headers. xAI dashboard API keys do not authenticate Grok Bot. Production gateway destinations are limited to the domains accepted by the pinned CLI. Loopback development requires explicit opt-in. All credential storage requires OS protection: macOS Keychain, Windows DPAPI, or a Linux Secret Service. Saved sessions can also travel through Stoke's encrypted vault when you explicitly enable agent account sync; see [account sync](account-sync.md). Loopback development sessions stay local. Receiving accounts does not install or enable the plugin.

When the desktop app exposes one session at a time, switch its login before each import. Import as new account saves another profile; Replace updates an existing profile when reconnecting. Stoke does not offer a separate Grok username/password login form. The plugin uses the desktop session, as documented by [grok-bot-cli](https://github.com/ScriptedAlchemy/grok-bot-cli#install).

Bot access and coding CLI access are separate. For three Cursor accounts and two Grok accounts, import the five actual Grok Bot desktop sessions and nickname them “Cursor 1”, “Cursor 2”, “Cursor 3”, “Grok 1” and “Grok 2”. Configure Cursor CLI accounts under Settings → Accounts → Cursor and Grok Build accounts under Settings → Accounts → Grok Build. A saved bot session does not sign in either coding CLI. Cursor's account manager currently supports separate API-key profiles; the Existing setup row uses its native browser login. Grok Build has separate login homes and API-key profiles.

The [official Grok Bot account guide](https://cursor.com/help/grok-bot/supergrok) explains that an individual Grok subscription grants bot usage through its linked Cursor/Bot account; a self-serve Grok Business seat supports Sign in with Grok. Linking grants bot usage without granting a Cursor plan. A linked grant and Cursor plan on the same account do not create two usage buckets. Existing links should be reused when importing each actual desktop session.

### Grok Bot workspace in beta.9

Choose New session → Other agents → Grok Bot after enabling the plugin. The left list separates bots and groups, includes the saved-account selector, search and hidden-bot toggle, and can be collapsed. Choose a row to open its chat. Switching accounts or bots keeps drafts and unconfirmed-send warnings bound to that account and target. The workspace retains up to 16 other drafts in memory; drafts survive tab switching and moving to a separate window, but quit does not restore cloud tabs.

Chat renders Markdown bot replies, preserves literal user line breaks, supports Copy, and reads the most recent 40, 100 or 200 entries. Live updates poll the visible chat every six seconds, stop after a failed read and pause while a tools page is open. Auto-scroll follows the bottom while leaving earlier messages readable when you scroll up.

Use **+ New** to create a bot or a group with 1–6 member bots. **Bot settings** edits the selected profile, notifications, visibility and group members. Deletion requires an explicit confirmation identifying the bot or group. **Skills** shows the library shared by all bots in the selected account, imports pasted SKILL.md contents through an owned temporary file, and confirms removal of library skills. Managed/plugin skills must be changed at their source. **Approvals** reads pending cards from the latest 200 entries. Each Allow once or Deny click rechecks the card through the reviewed CLI. Stale requests are refused; accepting a truncated card requires the official Grok Bot app. Nothing is approved automatically.

**Computer** provides a handoff to the official desktop app through its registered grokbot protocol. Check that the desktop app is signed into the intended Cursor/Grok account, open Computer, then choose Take over. This does not switch the app’s account. The reviewed CLI has no desktop viewer/control command, and Stoke does not embed a VNC stream or give the renderer desktop credentials.


## SSH routes and Other machines

Settings → SSH hosts offers Find duplicate SSH routes. It compares resolved SSH configuration, preserves different users, ports, keys, proxy/jump settings and host behavior, and requires shared known host keys when endpoints differ. Active-session hosts are excluded. Merging is explicit and keeps the first host's stable ID, chooses a verified Tailscale/DNS alias for fallback when available, and retains alternative alias metadata. A literal direct IP is preferred over a Tailscale address when available.

Preferred direct IP can also be set per host. It changes SSH's Hostname option while retaining the alias's configuration identity. A bounded TCP probe selects the direct IP; if unreachable, Stoke uses the alias. It does not retry authentication failures or accept host keys automatically. Configured proxies/jump hosts retain control of reachability, so the local TCP probe is skipped for those routes. Interactive tabs, transfers, file browsing, managed-session requests and transcript reads use this selection.

“Show under Other machines” explicitly links a saved SSH host to a signed-in Stoke device. The sidebar groups those SSH routes with that device's shared sessions and orders direct IP routes first. Device identity, never a similar label, supplies the association. SSH opens a separate terminal to the machine; existing shared Stoke sessions continue to use their authenticated encrypted Hub relay.

## Account manager direction

The account architecture should distinguish Stoke identity, native agent/subscription logins, and shared API connections. An agent is a client; Anthropic, OpenAI, OpenRouter and custom gateways are providers. The next account improvement is a shared connection registry with compatible per-agent bindings, rather than copies of the same key in several agent profiles. That registry is still pending. Current named API profiles and key-copy flows remain per-agent.

Primary comparisons: [Zed API access](https://zed.dev/docs/ai/use-api-access), [OpenCode v2 provider accounts](https://dev.opencode.ai/v2/docs/cli/providers/), [Claude Code authentication](https://code.claude.com/docs/en/authentication), [Codex authentication](https://learn.chatgpt.com/docs/auth), and [Grok Build](https://docs.x.ai/build/overview). OpenCode v2 documentation is a design reference, not a promise that Stoke's currently detected OpenCode version implements those commands.

## Work mode

Work mode is a built-in plugin for fun: enable it in Settings → Plugins, then open it from the command palette ("Work mode") or the plugin's row. The window becomes a pretend IDE with two editors side by side, an explorer, tabs, a status bar and a build panel. Any key types the next few characters of a real file from the project of the tab in front, with its own indentation; moving the mouse moves the caret and adds whole lines. Press Esc twice to leave.

It only reads. Nothing is written to the project, nothing in it is run, and nothing it reads is synced or sent anywhere but the window. It never opens secret-named files (`.env*`, keys, certificates, files named for a secret, a password or a credential), files the project's git ignores, dependencies, build output, lockfiles, binaries, or data and config files (JSON, YAML, TOML, `.ini`). Markdown is offered as a type when the project has it, and read only once you pick it. Text shaped like a key or a token is masked as `[redacted]` before it reaches the window. That is a match on the text's shape and on known patterns, not a promise: a short password written into the code some other way is shown as it is written. So what it shows is the project's real code; use it where you would be fine showing that code. A tab with no project on this computer (a New tab with none chosen, an SSH tab, a private chat) types a bundled sample website instead. The file types to type, the characters per key and the build panel are set in its panel or its own menu (right-click), and remembered per project under a hash of the folder, never the folder's name. The left editor types the most-used type you picked, the right the next.
